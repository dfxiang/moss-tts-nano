# 销售报表汇总表（预聚合）

## 背景：报表为什么慢

销售报表要按商品 / 客户 / 销售员 / 日期聚合全量销售数据。在演示库口径下
（4.5 年、21.2 万张订单、160.8 万行明细），优化前实测：

| 接口 | 单发延迟 | 10 并发 |
| --- | --- | --- |
| `/api/reports/product-summary`（无缓存时） | 0.69s | — |
| `/api/reports/dashboard` | 0.49s | 1.0 ~ 4.96s，容器 CPU 打满 100% |
| `/api/reports/employee-summary` | 0.39s | — |
| `/api/reports/customer-summary` | 0.15s | — |

两类根因：

1. **每次请求都全量重算**——报表对百万行明细做聚合，翻一页就重算一次；
2. **把聚合搬进了 Python**——经营看板原本把 20 万行订单拉进进程再 `sum()`，
   这段是 CPU-bound，单进程 uvicorn 下会串行阻塞其他请求（实测并发时容器
   CPU 长时间贴 100%，而数据库侧同一条聚合只要 52ms）。

## 方案：明细为准 + 预聚合 + 按键重算

* `sales_order` / `sales_order_item` 是**唯一事实来源**；汇总表都是可随时重建的派生数据。
* 写路径（下单 / 取消 / 删除）只重算**受影响的那几个键**，不做全表重建。
* 重算是**幂等**的：先按主键删命中行，再从明细表重新聚合插入。

### 五张表（`app/models/rollup.py`）

| 表 | 主键 | 服务的报表 |
| --- | --- | --- |
| `sales_rollup_day` | 业务日期 | 每日 / 月度销售汇总、看板当日与当月 |
| `sales_rollup_product` | 商品 | 商品销售汇总 |
| `sales_rollup_customer` | 客户 | 客户销售汇总 |
| `sales_rollup_employee` | 销售员 | 销售员业绩（金额 / 单数） |
| `sales_rollup_employee_customer` | 销售员 × 客户 | 销售员业绩里的「成交客户数」去重计数 |

演示库行数：分别约 1,673 / 360 / 1,557 / 500 / 49,040 行。

### 写路径时序（`app/services/rollup.py`）

```
1. capture_order_keys(db, order)   # 改动之前记下受影响的日期/商品/客户/销售员
2. 业务写入（新增 / 取消 / 删除）
3. refresh_rollups(db, keys)       # 重算这些键，然后 commit
```

第 1 步必须在业务写入**之前**：订单取消或删除后就取不到它的原值了。这也解释了
为什么用「按键重算」而不是「正负累加」——重算只需要知道哪些键脏了，而且对任何
写路径都自愈（批量导入、手工修数之后重跑一次即可对齐）。

实测维护开销（4.5 年数据）：单张订单的增量重算 0.7ms 量级；重算某一天
（182 张订单）约 3.7ms；全量回填 5 张表约 2~4s。

## 落地与运维

```bash
# 首次上线 / 生成 mock 数据后必须回填一次，否则报表全为 0
docker exec medsales-api python scripts/rebuild_sales_rollup.py

# 只对账，不写库（夜间定时任务的用法）
docker exec medsales-api python scripts/rebuild_sales_rollup.py --check

# 只重算某一天（例如绕过 API 改过那天的数据）
docker exec medsales-api python scripts/rebuild_sales_rollup.py --date 2026-07-30
```

对账比对的是总量口径（金额合计、订单数、去重键数量），见
`check_consistency`。服务启动时若发现「汇总表为空但已有订单」，只打一条告警，
不自动重建（重建耗时随历史增长，不适合放在启动路径）。

## 优化后实测（同一台机器、同一份数据）

| 接口 | 优化前 | 优化后 |
| --- | --- | --- |
| `/api/reports/dashboard` | 0.49s | 0.030s |
| `/api/reports/product-summary` | 0.69s（冷） | 0.008s，且不再有 60 秒陈旧窗口 |
| `/api/reports/employee-summary` | 0.39s | 0.014s |
| `/api/reports/customer-summary` | 0.15s | 0.019s |
| `/api/reports/sales-monthly` | 0.056s | 0.021s |
| 10 并发看板（总墙钟 / 最慢一条） | 4.98s / 4.96s | 0.23s / 0.22s |
| 下单 / 删除订单（含增量维护） | — | 96ms / 47ms |

`product-summary` 原先那个 60 秒进程内缓存已删除：读汇总表只要 8ms，缓存带来的
收益远小于它引入的陈旧窗口与多进程不一致问题。

## 已知边界

* **退货不计入这些口径**。报表口径是「非取消订单」的销售额，退货单不参与；
  若将来要算净销售额，需要把 `sales_return` 纳入重算范围。
* **应收余额不走汇总表**。应收 = Σ max(订单金额 - 已收金额, 0)，是对每张订单取
  max 后再求和，且收款会改动历史订单，无法用「按订单日期」的可累加列表达；
  现在是一条 SQL 聚合（约 52ms），不再拉进 Python。
* **汇总表粒度决定收益**。细粒度（日期 × 商品，42 万行）读一次要 81ms，粗粒度
  （商品，360 行）只要 0.24ms。当前按各报表实际需要的维度建表；将来若要支持
  「按任意区间看客户排名」这类查询，再补日期 × 客户粒度的表，不要直接把事实
  表物化一遍。
* **`/api/reports/order-detail` 未优化**（约 0.27~0.37s，瓶颈是对 160 万行明细
  做七表 join 的 `count(*)` 分页计数）。它需要的是「计数与明细解耦」，与汇总表
  方案无关，留待后续。
* 多实例部署时汇总表天然共享（都在数据库里），不像进程内缓存那样每个副本各存
  一份、失效只能清自己。
