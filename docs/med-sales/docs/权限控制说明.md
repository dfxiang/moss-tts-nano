# 权限控制说明（med-sales）

> 面向开发与运维：说明本系统「谁能做什么」的实现方式、内置约束、扩展步骤与验证方法。

## 一、总体设计

权限模型是经典的**用户 → 角色 → 权限**三级结构（表：`users` / `roles` / `permissions`，
关联表 `user_roles` / `role_permissions`）。一次访问会在四个层面被约束，且**共享同一套权限编码**：

| 层面 | 实现位置 | 作用 |
| --- | --- | --- |
| 接口级（强制） | 后端 `api/app/api/deps.py` 的 `require_permission()`，挂在路由 `dependencies` 上 | 未授权直接 403，是唯一的安全边界 |
| 路由级 | 前端 `frontend/src/router/index.ts` 的 `meta.permission` + 全局前置守卫 | 无权限时跳转 `/403`，不做无谓请求 |
| 菜单级 | 前端 `frontend/src/layout/MainLayout.vue` | 只显示有权限的菜单与分组 |
| 按钮级 | 指令 `v-permission` / `CrudPage` 的 `managePermission` | 隐藏无权操作的按钮（交互收敛） |

> 前端的三层都只是「界面收敛」——真正拦截在后端。绕过前端直接调用接口一样会拿到 403。

### 1.1 候选数据接口（`/api/options/*`）：登录即可访问

下拉框 / 搜索控件需要的候选数据（客户、商品、分类、厂家、供应商、仓库、员工、部门）
走独立的一组接口，**只要登录就能访问，不要求 `xxx:view` 权限**：

```bash
GET /api/options/{entity}              # 全部候选（可按 keyword 模糊匹配）
GET /api/options/{entity}/{item_id}    # 单个候选（编辑态回填显示文本）
```

两条硬约束：

1. **只返回 `id` / `code` / `name`**（`api/app/schemas/options.py`）。管理页列表接口返回
   的是完整业务字段——商品成本价、客户联系方式与信用额度、供应商账期、员工手机邮箱——
   这些字段不能进候选接口，否则等于把它们交给所有登录账号；
2. 管理页接口的权限模型不变（`customer:view` / `product:view` …）：
   候选接口是"字典"，不是数据出口。

这样处理的起因：报表页按 `report:view` 开放，但筛选控件原先直接调 `/employees` 之类的
管理接口（需要 `org:employee:view`），于是「页面有数据、却弹出权限不足」；而放开管理接口
又会泄露成本价与客户名单。前端候选统一由 `frontend/src/utils/catalogOptions.ts` 提供，
页面不要再自己 `fetchAllOptions('/products')` 这类全量拉取。

> 少数控件（开单 / 采购 / 退货弹窗的单价）需要商品价格：它们按 `product:view`
> **懒加载**商品档案里的价格，拿不到时留空由用户自己填，不走候选接口。

## 二、权限编码约定

编码形如 `模块:动作` 或 `模块:对象:动作`，**第一段即模块名**，前端据此分组展示：

```
sales:view            查看销售订单
sales:manage          维护销售订单（下单/发货/取消/删除）
system:user:manage    维护用户（新增/编辑/删除/分配角色）
```

内置通配权限 `all`（「全部权限」，绑定在「管理员」角色上）可访问全部接口，**不可删除、
不可从角色上移除**，避免把管理员自己锁在系统外。

阅读权限与维护权限分开登记：只给 `*:view` 的账号可以看，但改不了。

## 三、内置权限清单

清单在 `api/app/core/permissions.py` 的 `PERMISSION_CATALOG` 中定义，服务启动时由
`sync_permission_catalog()` **幂等补建**（只新增缺失项，不改动、不删除既有记录），因此权限管理页
始终能看到完整的能力字典。

| 模块 | 权限编码 |
| --- | --- |
| 内置 | `all` |
| 工作台 | `dashboard:view` |
| 系统管理 | `system:user:view` `system:user:manage` `system:role:view` `system:role:manage` `system:permission:view` `system:permission:manage` `system:log:view` |
| 组织与员工 | `org:department:view` `org:department:manage` `org:employee:view` `org:employee:manage` |
| 客户管理 | `customer:view` `customer:manage` |
| 商品管理 | `product:view` `product:manage`（含分类、厂家、调价） |
| 供应商管理 | `supplier:view` `supplier:manage` |
| 仓库管理 | `warehouse:view` `warehouse:manage` |
| 采购管理 | `purchase:view` `purchase:manage`（含收货入库） |
| 销售管理 | `sales:view` `sales:manage`（含发货、取消） |
| 库存管理 | `inventory:view` `inventory:manage`（期初建账） |
| 退货管理 | `return:view` `return:manage`（含退货入库） |
| 财务 | `finance:view` `finance:manage` |
| 报表分析 | `report:view` |
| GSP 合规 | `gsp:view` `gsp:manage`（含证照审核、附件归档） |

## 四、内置安全约束

接口层除了权限判定，还对这些高危动作做了保护（返回 400 并给出原因）：

| 约束 | 说明 |
| --- | --- |
| 不能删除/停用当前登录账号 | 防止误操作把自己踢出系统 |
| 必须保留至少一个可用管理员 | 删除或停用最后一个具备 `all` 的账号会被拒绝；把自己从管理员角色上摘掉同样会被拒绝 |
| `all` 权限不可删除 | 内置通配权限受保护 |
| `all` 不可从角色上移除 | 若角色当前含 `all`，保存权限时漏勾会被拒绝（需改用其他角色降权） |
| 角色仍被账号使用时不可删除 | 提示剩余账号数，要求先解除关联 |
| 权限仍被角色使用时不可删除 | 提示剩余角色数，要求先解除关联 |

系统管理中的用户/角色/权限变更都会写入审计日志（`module=system`），可在「操作日志」页按模块查询。

### 不挂权限编码的接口

除上述受控接口外，系统还有两类"刻意不做权限判定"的接口。它们不是权限漏洞，而是能力本身
就限定在"本人"或"公开资源"上，实施时必须同时满足表中的约束：

| 接口 | 可见范围 | 约束 |
| --- | --- | --- |
| `GET/PUT /api/auth/me`、`PUT /api/auth/me/password`、`PUT/DELETE /api/auth/me/avatar` | 仅当前登录用户 | 只作用于 `CurrentUser`，请求体里没有目标用户 ID；用户名 / 启用状态 / 角色 / 员工归属均不可写 |
| `GET /api/avatars/{filename}` | 匿名任何人 | 文件名白名单正则 + 对象键前缀固定为 `avatar/`，两者同时成立才放行；不匹配一律 404，避免变成"任意对象下载器"（同 bucket 内有 GSP 证照扫描件） |

管理员重置他人密码（`POST /api/users/{id}/reset-password`）**属于受控接口**（`system:user:manage`），
它不校验原密码、不做二次确认，等价于"账号接管"能力，因此额外用独立审计 action
`reset_password` 留痕。自助改密（`PUT /api/auth/me/password`）则相反：必须校验原密码 + 新密码两次一致。

## 五、初始化与角色模板

```bash
# 1) 初始化/重置管理员账号（同时会同步权限清单，并给「管理员」角色绑定 all）
cd api
.venv/bin/python scripts/create_admin.py --username admin --password admin123

# 2) 同步权限清单；--with-roles 顺带创建角色模板（销售员/采购员/仓管员/财务/质量管理）
.venv/bin/python scripts/seed_permissions.py --with-roles

# 容器部署环境
docker compose exec medsales-api python scripts/create_admin.py --username admin --password admin123
docker compose exec medsales-api python scripts/seed_permissions.py --with-roles
```

两个脚本都是幂等的：已存在的权限按编码跳过、已存在的角色按名称跳过，重复执行安全。

## 六、扩展方式

### 新增受控接口

1. 在 `PERMISSION_CATALOG` 登记编码（若模块已有 `*:view` / `*:manage` 可直接复用，无需新增）；
2. 在路由装饰器上挂依赖，函数签名无需改动：

```python
@router.post("/orders/{order_id}/audit",
             dependencies=[Depends(require_permission("sales:manage"))])
async def audit_order(...): ...
```

3. 需要「任一权限即可」时传入多个编码：`require_permission("system:role:view", "system:user:manage")`。

### 新增页面 / 按钮控制

```ts
// 路由
{ path: 'sales/orders', component: ..., meta: { title: '销售订单', permission: 'sales:view' } }
```

```html
<!-- 按钮：无权限时隐藏 -->
<el-button v-permission="'sales:manage'">新增销售单</el-button>

<!-- CrudPage 页面：一行配置即可控制「新增/编辑/删除」 -->
const config = { title: '客户管理', api: customerApi, managePermission: 'customer:manage', ... }
```

菜单项同理，在 `MainLayout.vue` 的 `menuGroups` 中给条目补 `permission` 字段。

## 七、边界：只做功能权限，不做数据级权限

本项目实现的是**功能权限**——控制「谁能访问哪个模块 / 接口 / 按钮」；**不实现数据级（行级）权限**——
不控制「谁能看到哪些行数据」。这是设计边界，不是待办事项：

- 账号只要拥有 `customer:view`，客户列表里的全部客户都可见；不存在「销售员只能看本区域客户/订单」
  这类按区域、部门或归属人过滤的能力。
- 权限粒度到「模块 + 读/写」为止（如 `sales:view` / `sales:manage`），不细分到单条记录的归属权。
- 确有按区域/部门隔离数据的需求时，请在部署侧自行实现（例如网关或只读视图），本项目不提供该能力。

## 八、验证方法

```bash
# 后端：权限校验、通配权限、内置约束的单元测试
cd api && .venv/bin/python -m pytest -q tests/test_permissions.py

# 前端构建 + 运行环境回归
cd frontend && npm run build
cd frontend && npx playwright test --config playwright.live.config.ts
```

手工核对最快的方式：新建一个不分配任何角色的账号，登录后应只能看到 `/403` 提示页；
再用管理员给它绑定一个只含 `system:user:view` 的角色，此时用户管理页可读，但「新增」按钮消失、
直接调用 `POST /api/users` 返回 403。
